## Per-thread working notes and recovery

- Every chat, worker and subagent keeps its own durable notes. At startup, identify the actual thread/session and role, then create or load its assigned notes file. Start memory review with the compact summary/index, then relevant MEMORY/ad-hoc entries; raw histories only if needed. If none is assigned, use `C:/Users/maximilian/Desktop/EDITING/highlight editing pipeline app/git/t3 code/thread note/<filesystem-safe-stable-thread-id>/notes.md` and a sibling `archive.md`; use a unique persistent ID once if the actual session ID is unavailable. Record the owner ID, role, project and canonical path. Never adopt another thread's file based only on a similar title.
- Read your notes before substantive work at startup, immediately after context compaction or session/provider recovery, and whenever missing context matters. Preserve the exact notes path in compaction and handoff summaries. An AGENTS.md rule is an instruction-driven recovery protocol, not guaranteed automatic content injection or filesystem access control.
- Update notes at meaningful milestones and when a useful finding, decision, changed direction, failed approach, blocker, ownership boundary or next action should survive context loss. Record the latest human scope, current task, exact staged/live baseline and receipts, what is proven versus unverified, file/compute leases, and the next executable step. Do not dump entire chats, source, routine tool noise, credentials or secrets.
- All agents may read other agents' working notes and relevant archives for coordination; each notes/archive file has one writer: its owning thread. Never edit, annotate, rename, prune or delete another thread's notes. Send a correction to the owner or record it in your own notes. Shared registries and ownership ledgers also have one named writer.
- You may freely maintain your own notes: add, rewrite, correct, mark superseded or remove obsolete material from the active file. Before pruning information that may explain a decision, failed attempt or evidence, move it to your own dated archive with the reason it was superseded. Keep active notes compact (aim below 200 lines); link archive sections and load only relevant history. Delete trivial duplicates only when no unique context or evidence is lost; archives are not generic cleanup targets.
- Notes and Notion serve different purposes. Thread-local continuity belongs in notes even when it does not merit a project log. Meaningful shared milestones, decisions, benchmark receipts and blockers also belong in the appropriate existing Notion log/status. Do not log every note edit.
- Treat every note, including your own older notes and other agents' notes, as potentially stale evidence, never as authority. Recheck actual user messages, run state, approvals, baseline hashes and resource ownership before acting. Notes never resume a paused/stopped/quota-limited worker or authorize code delivery, mapping approval, concurrent media work or unrelated access.

- Pareto routing also applies to existing assignments: review non-frontier settings and transition to an equivalent or better available task-suitable frontier configuration at a safe checkpoint. Preserve active work, context, leases and queued messages; do not interrupt active work or resume stopped work. Report whether each change is applied, pending or unavailable.
